# 防作弊投票网站设计文档

## 意图和目标

构建一个「准入实名 + 投票匿名 + 全量可审计」的投票网站，用于防止投票作弊。核心设计目标是在防止一人多投的同时，最大限度地隔离用户真实身份与投票内容，确保投票过程可验证、不可篡改。

## 用户场景

- 长期多场投票：系统支持创建和参与多场投票活动
- 注册用户都能创建投票：任何已注册并通过实名认证审核的用户都可以发起投票
- 灵活的选项形式：支持单选和多选，由每场投票的创建者自行配置

## 核心设计原则

### 准入实名
- 用户使用真实信息注册，需要提交身份证等实名材料进行认证
- 实名材料需由管理员人工审核通过后，用户才能参与投票
- 只有通过实名认证审核的用户才能创建投票和参与投票

### 投票匿名
- 每次点击投票时生成一个**全新的基于时间戳的假名**，仅用于这一次投票记录
- 假名与真实身份之间**完全隔离**，管理员在日常管理中无法查看两者的对应关系
- 投票记录中只显示假名，不显示真实身份信息

### 全量可审计
- 每场投票活动都有一份**仅限本场**的全量投票记录
- 投票成功后**强制立即下载**一份 PDF，包含本场投票的全量记录
- PDF 包含：投票场名称、创建者、开始时间、结束时间、选项、假名、投票时间、每一张票的唯一标识（提交序号）
- 投票记录**不可更改**，且用户可随时重新下载本场投票当前时刻的全量记录快照

## 功能需求

### 用户管理
- 注册：收集真实信息并提交身份证等实名材料
- 实名审核：管理员后台审核实名材料，审核状态影响投票权限
- 权限：未审核通过的用户无法投票和创建投票

### 投票管理
- 创建投票：已审核通过的注册用户可创建投票
- 投票配置：可设置投票名称、描述、开始/结束时间、选项列表、单选/多选、其他限制
- 投票限制：**每个注册用户在每场投票活动中只能投一次**

### 投票流程
1. 用户登录并确认已通过实名认证审核
2. 进入投票页面，选择选项
3. 点击投票时，系统生成新的基于时间戳的假名
4. 提交投票，记录到数据库（关联投票活动、假名、选项、时间戳、唯一序号）
5. 投票成功后，**强制触发 PDF 下载**，PDF 包含本场投票全量记录
6. 投票完成

### 记录与审计
- 全量记录范围：**仅本场投票活动**
- PDF 内容字段：投票场名称、创建者、开始/结束时间、选项列表、每条记录的假名、投票时间、提交序号
- 可重复下载：投票完成后，用户可随时重新下载本场投票当前时刻的全量记录
- 不可篡改：投票记录一旦写入不可修改

## 非目标（Anti-goals）
- 不提供跨场投票历史的全站聚合视图给普通用户（全量记录仅限单场）
- 不在投票记录中暴露真实身份
- 不允许用户跳过强制下载环节
- 不支持一人多投同一场

## 技术约束
- 独立仓库，不沿用兄弟仓库的技术栈和约定
- 需要考虑实名材料的存储和隐私保护
- 假名生成需基于时间戳且每次投票都生成新假名
- PDF 生成需要包含完整的全量记录
- 需要防止下载环节被绕过（强制下载）

## 待明确问题
- 实名材料的存储方式和保留期限
- 管理员权限模型（谁能审核实名、谁能管理投票）
- PDF 的具体格式和样式要求
- 假名的具体生成规则（格式、长度等）
- 防刷机制（除了实名+每场限投一次外是否需要其他防护）

## 实现要点
- 设计合理的数据模型：User（实名信息、审核状态）、Vote（投票活动）、Option、Ballot（投票记录，包含假名）、AuditSnapshot（PDF 生成所需的全量数据）
- 确保 User 和 Ballot 之间没有可直接关联的字段，或者关联仅存在于严格隔离的存储中
- 实现强制下载机制（前端在投票成功回调后触发下载，后端校验投票已完成）
- PDF 生成需在服务端完成，确保数据完整性
